# 1일 1일기 올인원 흐름

기획부터 개발까지를 여섯 단계로 잇는다. 각 단계는 이미 있는 Spec Kit 스킬과 이 저장소의 규칙을 그대로 쓰고, 이 스킬은 순서와
멈추는 곳, 이 앱에서만 필요한 것을 정한다.

## 입력

```text
$ARGUMENTS
```

- 새 기능 설명이면 1단계부터 한다. 예: `홈 화면 위젯`.
- 기존 스펙이면 번호나 폴더(`001`, `specs/001-renewal-baseline`)를 받는다. 시작 단계(`기획부터`, `계획부터`, `프로토타입부터`,
  `디자인부터`, `점검부터`, `개발부터`)와 범위(`US2`, `T045`, `쓰기 화면`)를 같이 받을 수 있다.
- 비어 있으면 0단계로 지금 상태를 보고 어디서 이어 갈지 사용자에게 묻는다.

## 언제나 지키는 것

- 답과 진행 안내는 한국어로 한다.
- 기능을 만들거나 고치는 모든 단계에서 사용자가 말하지 않아도 레퍼런스를 실제로 찾아 근거로 삼는다. 화면과 흐름은 토스, 당근, 배민과
  해외 앱(Apple, Material, Day One, Journey, Daylio, Things, Bear 같은), 일기 기능은 국내외 일기 앱이다. 공식 문서, 스토어, 지원 페이지,
  디자인 시스템 문서, 공식 기술 블로그에서 확인한 것만 출처와 함께 적고 확인하지 못한 것은 못 했다고 쓴다. 남의 앱을 그대로 베끼지 않는다.
- 기능을 제안하거나 받기 전에 `CLAUDE.md`의 "지켜야 할 선"과 `.specify/memory/constitution.md`를 본다. 요청이 선을 넘으면 그 자리에서
  멈추고 어느 원칙에 걸리는지 말한 뒤 묻는다(쓰던 무료 기능을 유료로, 일기 내용을 밖으로, 원본을 지우는 복원 같은 것).
- 일기·사진·설정을 읽거나 쓰는 기능이면 `docs/migration.md`와 `docs/backup.md`를 먼저 본다. 저장 형식이 바뀌면 이전 코드, 백업 형식
  버전, 복원 호환을 같은 스펙에서 다룬다.
- 단계가 끝날 때마다 결과를 보여 주고 다음 단계로 간다. 사용자가 "멈추지 말고 끝까지"라고 하면 단계 사이에서는 묻지 않되, 아래
  "꼭 묻는 곳"에서는 묻는다.
- 규칙(지켜야 할 선, 색 토큰, 화면 구조, 저장 형식, 무료/유료 범위)이 바뀌면 그 규칙이 있는 문서와 헌법, 스펙을 같은 커밋에서 고치고
  `docs/DECISIONS.md`에 날짜와 까닭을 남긴다.
- 커밋과 푸시는 사용자가 요청할 때만 한다. 커밋 전에 `git status`로 보고 이번에 고친 파일만 담는다.

꼭 묻는 곳:

- 저장 형식(DB 스키마, 백업 형식)을 바꿀 때
- 무료/유료 경계나 광고 자리를 정하거나 바꿀 때
- `docs/DECISIONS.md`의 열린 결정을 닫을 때
- 유료 구간이 있는 서비스나 라이브러리가 나올 때(무료 한도부터 적는다)
- 프로토타입이나 Figma 화면이 지금 앱과 크게 달라질 때(기존 사용자가 길을 잃는 변경)

## 0단계: 지금 상태 보기

1. `.specify/feature.json`, `specs/` 목록, `git status`, 지금 브랜치를 본다.
2. 대상 스펙 폴더에 무엇이 있는지로 이어 갈 단계를 정한다.

| 있는 것 | 이어 갈 단계 |
| --- | --- |
| 스펙 없음 | 1단계 |
| `spec.md`만 | 2단계 |
| `plan.md`까지, `tasks.md` 없음 | 2단계의 작업 목록부터 |
| `tasks.md`까지, `prototype.md` 없음 | 3단계(Figma 프로토타입) |
| `prototype.md`까지 | 4단계(Figma가 남았으면) 또는 5단계 |
| Figma 화면까지, `design-review.md` 없음 | 5단계의 디자인 점검부터 |

3. 인자로 시작 단계를 줬으면 그걸 따른다. 앞 단계 문서가 없으면 그 사실을 말하고 앞 단계부터 할지 묻는다.

## 1단계: 기획(스펙)

1. 스펙을 쓰기 전에 같은 기능을 레퍼런스 앱이 어떻게 하는지 찾아 정리한다. 무엇을 보여 주고 무엇을 빼는지, 빈 상태와 실패, 무료/유료
   경계를 어떻게 두는지. 이 정리를 스펙의 근거로 적는다.
2. 새 기능이면 `/speckit-specify`에 기능 설명을 넘긴다. 브랜치를 새로 만들면 `<type>/<영문-슬러그>`를 쓴다.
3. `/speckit-clarify`로 애매한 곳을 묻는다. 답은 스펙의 Clarifications에 남기고 규칙이 바뀌는 답이면 규칙 문서와 DECISIONS도 고친다.
4. 스펙 요약(사용자 이야기와 우선순위, 새 요구사항, 지켜야 할 선에 닿는 곳, 무료/유료)을 보여 준다.

## 2단계: 계획 문서

1. `/speckit-plan`을 부른다. 새 기술을 고르지 않고 `CLAUDE.md`와 `docs/`의 결정을 따른다. 정하지 않은 것은 정하는 조건과 함께
   `research.md`의 열린 결정으로 둔다. Constitution Check는 원칙마다 이 계획에서 지키는 자리를 적는다.
2. `/speckit-checklist`로 요구사항 품질을 본다(Spec Kit 스크립트가 `plan.md`를 요구해서 계획 뒤에 한다). 저장 형식이 바뀌는 기능이면
   "이전·백업·복원" 체크리스트를 꼭 만들고, 걸린 항목은 스펙이나 규칙 문서를 고쳐 닫는다.
3. `/speckit-tasks`를 부른다. 남은 일은 사용자 이야기 순서다. 실제 파일 경로를 쓰고, 프로토타입과 Figma 작업은 "화면" 페이지의 섹션 이름을 경로로 쓴다.
4. `/speckit-analyze`로 스펙, 계획, 작업 목록이 서로 맞는지 보고 어긋난 곳을 고친다.
5. 문서에 적은 파일, 함수, 테스트 이름이 실제로 있는지 `grep`으로 확인한다. 없는 걸 있다고 적지 않는다.

## 3단계: 프로토타입 (Figma)

먼저 확인한다: `docs/design.md` 상태가 "확정"이 아니면 화면을 그리지 않는다. 디자인 시스템부터 만든다(사용자 요청 2026-10-31).

1. 레퍼런스의 시각 규격을 공식 문서의 숫자로 조사한다: 토스 TDS, 당근 SEED, 배민, Apple HIG, Material 3와 그 밖의 유명 플랫폼. 흐름 조사와 따로 묻는다.
2. 색은 기존 1일1일기 정체성(라벤더·라일락, 기분 파스텔)에서 출발한다.
3. "디자인 시스템" 페이지에 색 단계, 글자 단계와 굵기, 간격, 모서리, 핵심 컴포넌트(버튼, 목록 줄, 칩, 시트, 탭 바)를 시안 둘 이상으로 나란히 그리고, 값마다 근거를 옆에 적는다.
4. 사용자가 고르면 `docs/design.md`를 "확정"으로 바꾸고 `docs/DECISIONS.md`에 남긴 뒤 아래로 간다.


목적은 흐름을 손으로 눌러 보고 고치는 것이다. 프로토타입은 Figma에서 만든다(사용자 결정 2026-10-31). 다듬는 것은 4단계에서 한다.

1. 스펙의 사용자 이야기마다 지나가는 화면을 나열하고 화면 흐름(어디서 어디로, 뒤로 가면 어디)을 `specs/<번호>/prototype.md`에 적는다.
2. Figma "1일 1일기"의 "표지 · 흐름" 페이지에 섹션 "프로토타입 · <스펙 이름>"을 만들고 화면 프레임(폰 390×844, 넓은 화면 1024×720)을
   흐름 순서대로 둔다. 색과 글자는 "디자인 시스템" 페이지의 변수·글자 스타일을 쓴다(없으면 `docs/design.md` 초안 값으로 먼저 만든다).
3. 프레임 사이를 Figma 프로토타입 연결(누르기 → 이동, 시트는 오버레이, 뒤로는 Back)로 잇고 흐름 시작점을 둔다. 사용자는 Figma의
   프레젠테이션 보기로 눌러 본다.
4. 빈 상태, 실패, 권한 거부, 첫 실행, 이전 중, 오프라인 상태를 빠뜨리지 않는다. 고를 것(액센트 색 같은 것)은 같은 화면을 나란히 둔다.
5. 캡처해 사용자에게 보내고, 흐름을 확정하면 `prototype.md`에 확정 날짜와 바뀐 점을 적고 스펙에 되먹인다. 흐름이 바뀌면 `tasks.md`도 고친다.

## 4단계: 디자인과 Figma 기획문서

준비:

1. 메모리의 `figma-design-file`이 있으면 읽는다. 없으면 오발있 프로젝트 메모리의 같은 이름 문서(파일 구조와 Figma Console MCP 함정)를 참고한다.
2. `figma_get_status`(필요하면 `ToolSearch`로 figma-console 도구를 불러온다)로 Desktop Bridge 연결을 본다. 안 붙어 있으면 사용자에게
   Figma 파일 "1일 1일기"에서 Desktop Bridge 플러그인을 실행해 달라고 한다. 이 도구는 파일을 새로 만들 수 없다.
3. 무료 플랜은 파일 하나에 페이지가 셋까지다. "표지 · 흐름", "디자인 시스템", "화면" 세 페이지만 쓴다.

디자인 시스템(처음 한 번, 그 뒤로는 바뀔 때만):

1. `docs/design.md`의 토큰을 변수로 만든다. 무료 플랜은 컬렉션에 모드가 하나라 "색 · 라이트", "색 · 다크" 두 컬렉션에 같은 이름의
   변수를 둔다. 글자 스타일, 간격, 모서리, 그림자도 만든다.
2. 컴포넌트는 반복되는 것부터: 탐색(하단 탭, 내비게이션 레일, 상단 바), 버튼, 목록 줄, 일기 카드, 기분·날씨 선택, 시트, 토스트,
   빈 상태, 설정 줄. 폰과 태블릿 변형을 같이 둔다.

화면마다:

1. 그리기 전에 확정된 프로토타입, 스펙의 그 이야기, 지금 앱 화면(에뮬레이터 스크린샷)을 본다. 같은 화면을 레퍼런스 앱이 어떻게 두는지
   찾고, 배치를 바꾸는 안은 같은 패턴을 찾은 것만 출처와 함께 낸다. 고를 일이 있으면 시안을 나란히 보여 준다.
2. "화면" 페이지는 기능별 큰 섹션 일곱 묶음(1 시작, 2 일기, 3 Plus와 광고, 4 잠금, 5 기록 이전, 6 설정, 7 백업)을 왼쪽부터 쓰는 순서로 둔다. 화면은 맞는 묶음 안에 한 줄씩 아래로 쌓는다.
   줄 왼쪽은 섹션 "<화면 이름> (Sx)"에 [라이트 폰 화면과 왼쪽 여백의 번호 | 화면 설명 패널 | 다크 폰 화면 | 태블릿 화면]이고, 옆 섹션 "<화면> 상태"에 상태별 화면과 "언제 뜨는지"(`state/when`), "무엇을 하는지"(`state/what`) 설명을 둔다.
   단정형이고 근거(스펙 이야기, 문서 절)를 적는다.
3. 색은 변수, 글자는 글자 스타일, 반복되는 것은 컴포넌트 인스턴스로 쓴다.
4. 다 그리면 캡처해서 확인하고(겹침, 잘림, 넘침) 사용자에게 보낸 뒤 다음 화면으로 간다. 설명은 `docs/design.md` "Figma 화면 설명"을 따르고, 페이지 맨 위의 섹션 밖 조각과 겹친 섹션도 찾는다.
5. "표지 · 흐름" 페이지의 화면 흐름 지도와 진행 현황 표를 고친다.

디자인이 지금 앱과 크게 달라지면 먼저 묻고 DECISIONS에 남긴다. 화면 문구의 원본은 코드의 문자열 리소스다. Figma 문구를 복사해 쓰지 않는다.

## 5단계: 개발 (디자인 점검 먼저)

먼저 디자인 점검을 한다(사용자 요청 2026-11-01, 헌법 V). 디자인 시스템이 하나로 통일되어야 하므로 건너뛰지 않는다. 화면이 없는 작업(빌드,
모듈, DB, 이전 코드)은 점검 없이 해도 되고, 디자인 시스템 코드나 화면 코드를 쓰기 전에는 꼭 한다.

1. 이번 범위의 Figma "화면" 페이지 줄과 "디자인 시스템" 페이지, `docs/design.md`를 연다.
2. 레퍼런스 디자인 시스템의 공식 문서와 코드에 숫자로 대어 본다. 토스 TDS, 당근 SEED, Apple HIG, Material 3, 그리고 같은 화면을 가진
   유명 앱(Day One, Apple 저널 같은 일기 앱, 토스·당근의 같은 흐름)이다. 보는 것:
   - UI/UX: 흐름과 패턴(같은 일을 레퍼런스는 어떻게 두는지), 한 화면의 할 일과 강조 수, 빈 상태·실패·기다림
   - 수치: 화면 좌우와 줄 위아래 여백, 묶음 사이 간격, 글자 크기·굵기·줄 높이, 모서리, 터치 영역 크기(48dp, 44pt), 색 대비(본문 4.5:1)
   - 통일: 같은 역할에 같은 토큰과 컴포넌트를 쓰는지, 화면마다 따로 정한 값이 없는지, 폰·태블릿·다크가 같은 규칙인지
   - 문구: 해요체와 토스 UX 라이팅(`korean-copy-skills` 메모리)
3. 결과를 `specs/<번호>/design-review.md`에 표로 남긴다: 항목, 지금 값, 레퍼런스 값과 출처, 판단(그대로 또는 고침), 고친 곳.
4. 고칠 것이 있으면 개발 전에 고친다. 토큰이나 컴포넌트 값이면 `docs/design.md` → Figma 변수·글자 스타일·컴포넌트 → 그 값을 쓰는 화면
   순서로 고친다. 한 화면만의 문제면 그 화면을 고친다. 화면 하나를 맞추려고 따로 값을 두지 않는다. 바뀐 값은 `docs/DECISIONS.md`에 남기고,
   지금 앱과 크게 달라지거나 확정된 사용자 결정을 뒤집는 것은 먼저 묻는다.
5. 고친 화면을 캡처해 사용자에게 보여 준 뒤 개발로 간다.

그다음 개발:

1. `/speckit-implement`에 범위(이야기, 작업 번호)를 넘긴다. `tasks.md` 순서를 따르고 `[P]` 작업은 서브에이전트로 나눠도 된다.
2. 코드를 쓸 때 `CLAUDE.md`를 따른다. 자주 놓치는 것:
   - 화면 문구는 Compose 리소스 문자열에 둔다. Kotlin 문자열 상수 금지
   - 원시 hex와 `MaterialTheme.colorScheme`을 화면에서 쓰지 않고 디자인 시스템 토큰을 쓴다
   - 폰과 넓은 화면을 둘 다 그린다(창 크기 등급별 미리보기)
   - 일기 내용은 로그, 사용 통계, 비정상 종료 보고에 넣지 않는다
   - 저장 형식을 바꾸면 이전 시험과 백업 복원 시험을 같이 고친다
   - 주석은 자연스러운 한국말로 쓴다
3. 확인한다. 명령은 `CLAUDE.md`의 "빌드와 시험"에 있다(스펙 001이 프로젝트 뼈대를 만들면서 채운다). 설치는 에뮬레이터에만 한다.
   화면은 에뮬레이터 스크린샷을 Figma 화면과 나란히 보고 어긋난 곳을 고친다.
4. 끝난 작업은 `tasks.md`에 `[x]`로 표시한다. 실패한 검사는 출력과 함께 그대로 보고한다.

## 6단계: 마무리

1. 문서 동기화를 본다. 바뀐 규칙이 규칙 문서, 헌법, 스펙, DECISIONS에 같은 내용으로 있는지, `tasks.md`, 프로토타입, Figma 진행 칸이 맞는지.
2. 사용자가 커밋을 원하면 `CLAUDE.md` "커밋 규칙"(Conventional Commits, `<type>(<scope>): <한글 제목>`)대로 한다. 다른 세션의 변경이 섞였으면 무엇이 누구 것인지 말하고 담을지 묻는다.
3. 보고: 단계마다 한 것, 남은 작업 번호, 열린 결정과 물어볼 것.
